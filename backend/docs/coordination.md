### 답변 받은 것 / 확인 요청

- 🟡 **B 함수 시그니처 유지** (A가 호출): `validate_conditions`, `recommend`, `view_for`, `get_candidate`, `get_my_route`, `subway.search_stations`. 바꾸면 알려 주세요.
- 🟡 **후보 ID 형식 유지** `c_<날짜8>_<HHMM>_<역명>`. A 검증: 역명 1~30자, 공백·`/ \ ? # %` 없음 — **현재 데이터 279개 역은 모두 통과**(확인함).
- 🟡 **`no_candidate` 응답:** `reasons: [{date, code, message}]` (예: `NO_COMMON_TIME`). 코드 종류 목록을 알려 주세요(프론트 안내 문구에 필요).

### `met`(엘리베이터) 값 — 확인 결과
B의 `scripts/build_subway_data.py` 기준입니다. **기본값이 아니라 데이터에서 계산한 값**입니다.
- 1~8호선: 서울교통공사 *역별 승강설비현황*(`accessibility_raw.xlsx`)의 엘리베이터·에스컬레이터·휠체어리프트 **대수**.
- 9호선·우이신설선: 대수 자료가 없어, 서울시 *엘리베이터 위치정보*에 그 역 이름으로 등록된 점이 있으면 "있음"(점 개수를 대수로 사용).
- 환승역은 한 노선 이름으로만 집계된 경우 같은 역의 다른 노선 정보를 공유(`shared`, 현재 3개 노드).
- 역 판정: **`met` = 모든 노드의 엘리베이터 대수 > 0**, `unmet` = 0대인 노드가 있음, `unknown` = 정보 없는 노드가 있음. 결과: `met` 277 · `unmet` 1(도곡) · `unknown` 1(삼전).
- **해석 주의:** `met`은 "역에 엘리베이터가 1대 이상 있다"입니다. 아래는 **별개이며 아직 반영되지 않았습니다.**
  - 지금 작동하는지(가동 상태), 승강장↔출구가 계단 없이 이어지는지, 환승 통로가 계단 없이 이어지는지.
- 🟡 `unmet`(도곡)·`unknown`(삼전)이 자료 범위 밖(다른 운영기관 등) 때문인지 B가 확인해 주세요. 원인은 아직 모릅니다.

### 엘리베이터 · 접근성 개선 (제안)
- 🟡 **"엘리베이터 필요"와 "계단 회피" 구분:** 필요 = 엘리베이터 필수, 회피 = 엘리베이터 우선 + 에스컬레이터 허용(선호 점수). 지금은 같은 규칙. 데이터에 노드별 에스컬레이터(255개)·휠체어 리프트(30개)가 있으나 미사용.
- 🟡 **환승 통로:** 서울시 API 샘플(환승통로 엘리베이터 18건, 9호선 55건)은 **일부 역만** 있어 104개 환승 전체를 판단할 수 없습니다. 확인 안 된 환승은 `unknown` 처리 제안.
- 🟡 **가동·고장 상태:** 서울시 API는 "현재" 상태라 **미래 모임엔 약한 근거**입니다(당일=강한 조건, 미래=경고/감점 제안). 가동 상태를 주는 **서비스명은 아직 못 찾았습니다**(샘플 서비스에는 상태 필드 없음). 분담 제안: A가 가져오기·5분 캐시, B가 경로 판단에 반영.

## 2. 프론트엔드 (심빛나 · 박서연 님)

### 시작하기
- 🟢 **API 문서:** [api.md](api.md), 서버 실행 후 `/docs`(Swagger). 실행: `backend/`에서 `uvicorn app.main:app --reload` → `http://localhost:8000/docs`. 시드: `python -m scripts.seed --yes` (5단계 약속방 + 방마다 입장 코드·토큰, 호스트 비밀번호 `demo-password`).
- 🟡 **CORS:** 서버 환경 변수 `CORS_ORIGINS`에 프론트 주소 등록. 기본값 `http://localhost:5173`. 배포 주소가 정해지면 알려 주세요.
- 🟢 **인증:** 방마다 개인 토큰, `Authorization: Bearer <토큰>`. 토큰은 방 생성/참여/호스트 로그인 응답에서 **한 번만** 내려가므로 저장해 재접속에 사용. 쿠키 미사용.
- 🟢 **오류 형식 통일:** `{ "error": { "code", "message", ... } }`. 입력 오류 `422 VALIDATION_ERROR`(`fields`), 조건 오류 `422 CONDITIONS_INVALID`(`errors[].field`), 입장 코드 추측·호스트 비밀번호 실패 초과 `429`(`Retry-After`).

### 이미 반영된 변경 (시안·팀 결정)
- 🟢 **입장 방식 변경 (11/4 결정) — 프론트 작업 필요:**
  - **방 만들기 화면: "방 PIN을 설정해주세요" 입력칸을 제거**합니다. 서버에 `pin`을 보내면 `422`입니다.
  - 방 생성 응답의 `join_code`(8자, 예 `k7m2x9qa`)를 **생성 직후 호스트에게 보여 주고** 공유할 수 있게 합니다 (시안의 "MOMEET-…" 표기는 화면 표시용으로 붙여도 됩니다. 서버는 `MOMEET-` 접두사·대소문자·공백·하이픈을 무시합니다).
  - **참여 화면("방 PIN 또는 링크"):** 입력값이 링크면 코드만 뽑아, 코드면 그대로 `GET /join/{code}`(미리보기 카드) → `POST /join/{code}` + 닉네임(참여)으로 호출합니다. **방 ID를 URL로 쓰는 기존 참여 호출(`POST /meetings/{id}/join`)은 없어졌습니다.**
  - 마감 후 참여 신청(`202`) 응답에 `meeting_id`가 추가되었습니다 (`claim` 호출에 사용).
  - 인증 후 대시보드의 `meeting.join_code`로 **참여자도 "링크 복사하기"를 할 수 있습니다.**
  - 코드가 틀리면 `404 INVALID_CODE`(없음·형식 오류·만료 구분 없음), 연속으로 틀리면 `429`(`Retry-After`) — 안내 문구가 필요합니다.
- 🟢 **입력 제한:** 약속 이름 12자, 닉네임 8자, 방장 비밀번호 8자 이상, **최대 인원 10명, 날짜 범위 1~7일**.
- 🟢 **모집 중에도 조건 입력 가능** (시안의 "입력 중/입력완료" 목록과 일치).
- 🟢 **제안 응답 변경:** 거절 후에도 응답을 바꿀 수 있고("수정하기" = `POST /proposal/response` 재호출), 전원 응답 + 거절 있음이면 `proposal.needs_replan = true`. 호스트가 다른 후보를 재제안합니다.
- 🟢 **`proposal.status`에서 `rejected`가 사라졌습니다** (`pending`/`accepted`/`superseded`). `rejected`를 가정했다면 `needs_replan`/`rejected_count`로 바꿔 주세요.
- 🟢 대시보드에 `progress`("2/4 완료"), `proposal.accepted_count / rejected_count / responded_count`.

### 확인·합의 필요
- 🔴 **조건 입력 화면 이미지** 필요 (시안에 "내 조건을 입력해 주세요" 카드까지만). API 입력 형식이 화면과 맞는지 확인해야 합니다:
  `availability {날짜: [시 0~23]}`, `default_station`, `exception_stations [{date, hours, station}]`, `constraints {max_travel_min, max_transfers, max_walk_m, needs_elevator, avoid_stairs: {value, level: required|preferred}}`.
- 🔴 **티맵 ①②를 쓰려면 화면이 필요합니다** — [3절](#3-티맵-보행-경로-구간-12): 출발지(주소) 입력 위치, 약속 장소 입력 위치.
- 🟡 **추천 계산이 길 수 있음**(최대 조건 약 33초). 비동기 방식으로 가면 프론트가 "찾고 있어요" 상태를 폴링해야 합니다. [1절](#1-백b-유진-님) 결정 필요.
- 🟡 **화면 갱신 방식:** 서버 푸시(웹소켓) 없음 → 대시보드를 **주기적으로 재호출(폴링)** 해야 다른 참여자의 입력/응답이 보입니다. 주기(예: 5초) 합의 필요.
- 🟡 **추천 지도(시안 왼쪽 경로 그림):** 응답에는 구간(`segments`: 호선·승차역·하차역·정거장 수·소요시간)과 만남 역의 위경도가 있습니다. **경로를 선으로 그릴 좌표 목록은 없습니다.** 도식으로 충분한지, 좌표가 필요하면 B 요청.
- 🟡 **`accessibility` 표시 문구:** 서버는 `met`/`unmet`/`unknown`. 예: "엘리베이터 이용 가능 / 없음 / 확인 필요". (`met`은 "역에 엘리베이터가 있음"이며 **지금 작동한다는 뜻이 아님**을 문구에 반영)
- 🟡 **"엘리베이터 필요"와 "계단 회피" 라벨·설명** (B 안건과 연결).
- 🟡 **사이드 메뉴 "내 약속방 / 참여한 약속 / 설정":** 계정이 없어 서버에 목록 API가 없음 → 프론트가 (방 ID, 토큰)을 저장해 목록을 만드는 안 제안.
- 🟡 **초대 링크 형식:** 프론트 라우팅에서 결정 (예: `/m/{meetingId}`). 방 ID는 8자 URL-safe 문자열(`-`, `_` 포함 가능).
- 🟡 **마감 후 참여 신청**(호스트 승인) 화면을 만들지 ("참여자 편집"에 승인/제외를 넣을지).
- 🟢 **시간 표기:** 날짜 `YYYY-MM-DD`, 후보 시각 `HH:MM`(한국 시간 기준 값), 서버 기록 시각은 UTC `...Z`.

## 3. 티맵 보행 경로 구간 ①② (결정됨 — 구현 전 준비 사항)

**현재 확인된 것:** 키 유효, 보행자 경로 호출 성공(서울역→시청 1322m·약 19분), `searchOption=30`(계단 제외 의도) 요청 수락.
**확인 못 한 것:** ① **계단 제외가 실제로 적용되는지**(응답에 계단 표시 없음 — 계단이 확실한 구간으로 옵션 `0`/`30` 비교 필요), ② **하루 호출 한도**(SK Open API "상품 관리" 탭 확인 필요), ③ 주소→좌표 변환·장소 검색 API 사용 가능 여부.

| | ① 출발지 → 출발역 | ② 만남역 → 약속 장소 |
| --- | --- | --- |
| 필요한 입력 | 참여자가 출발지(주소 또는 위치) 입력 | 약속 장소(이름/주소) 입력 — **누가·언제 입력하는지 결정 필요** (제안: 호스트가 제안 시 또는 확정 후) |
| 필요한 변환 | 주소 → 좌표, 좌표 → 가까운 출발역 | 장소 → 좌표 |
| 호출 시점·양 | 조건 입력 시 참여자당 1회 (후보와 무관) | 장소 확정 후 참여자당 1회 |
| 추천 계산 반영 | 🟡 도보 시간을 이동시간에 더할지 (B의 모델 변경) — 우선 **표시용**, 후속에 계산 반영 제안 | 표시용 |
| 필요한 것 | 시안에 없는 화면 (출발지 입력), 기획·프론트 | 시안에 없는 화면 (장소 입력/표시) |

- 🔴 기획(신이슬 님): ①②의 입력 화면과 노출 위치.
- 🔴 A: 호출 한도 확인 후 호출량(참여자 10명 기준 ①≤10건, ②≤10건) 설계, 키는 서버 환경 변수에만 보관, 호출 실패 시 **기존 결과로 되돌아가고 사유를 응답/로그에 표시**.
- 🟡 환승 통로(지하) 계단은 티맵 대상이 아닐 수 있어 B의 환승 데이터 보강이 따로 필요합니다(미확인).

## 5. API 응답 이상 시 원인 보고 원칙

서버 API(우리)와 외부 API(서울시·티맵)가 제대로 응답하지 않으면, 아래 순서로 **원인을 특정해 보고**합니다. 추측은 "추정"으로 표시합니다.

| 증상 | 가능한 원인 | 확인하는 것 |
| --- | --- | --- |
| 외부 `401/403`, 인증 오류 코드 | 키 오류·미활성·상품 미신청 | `.env` 키 길이/공백, SK Open API 앱 활성·상품 관리, 서울시 인증키 종류 |
| 외부 `429`/한도 오류 | 호출 한도 초과 | 상품 관리의 일일 한도, 우리 호출량 |
| 외부 `200`이지만 데이터 0건/오류 코드 | 서비스명·인자 오류, 서비스 종료, 해당 데이터 없음 | 응답의 `RESULT.CODE/MESSAGE`를 그대로 인용 |
| 연결 실패/타임아웃 | 네트워크, 서비스 장애, 방화벽 | 재시도 결과, 다른 네트워크에서 재현 |
| 우리 API `4xx` | 입력 오류·권한·단계 불일치 | `error.code` ([api.md](api.md) 오류 코드 표), `fields`/`errors` |
| 우리 API `500 INTERNAL_ERROR` | 서버 내부 오류 | **서버 로그**(스택 포함, `momeet` 로거). 응답에는 상세가 없음 |
| 응답이 매우 느림 | 추천 계산 시간 | [1절](#1-백b-유진-님) 성능 표, 인원·날짜·시간 폭 |

- 🟢 **서버 로그:** 예기치 못한 오류는 요청 경로와 스택을 로그에 남기도록 했습니다(응답에는 내부 상세 없음). 비밀값(토큰·입장 코드·비밀번호·키)은 로그에 넣지 않습니다.
- 🟢 보고에는 "무엇을 호출했고(요청), 무엇이 돌아왔고(상태·코드), 추정 원인과 확인 방법"을 포함합니다. 키 값은 절대 포함하지 않습니다.
